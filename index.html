更新检查不再误报

  • d8d7cc068|fix(update): stop reporting bogus 'Found 9980 new commit(s)' on shallow installs

  • 54bd47b81|fix(desktop): show 'update available' instead of fake '1 change included' on shallow clones
  • 294071bf0|fix(banner): stop fabricating '1 commit behind' on SSH-official remotes

一批「更新状态报错」的修复，覆盖两类问题。第一类是 shallow 克隆（depth-1 安装器检出）：`rev-list --count HEAD..origin/main` 在截断的图上会走完整远端祖先链，报出荒谬的「Found 9980 new commit(s)」；修法是零/非零判断保留（0 在任何图上都可信），正数时用 GitHub compare API 恢复真实数字（9442a718d），取不到就换成不带数字的说法。第二类是本地领先（local-ahead）：SSH 快路径只比对 tip SHA，本地有 carry commit 时 SHA 不同就误报「1 commit behind」——用户被引导跑 hermes update 恰好会清掉本地未推送的工作；修法是对比祖先关系，ahead_by==0 视为 up to date，桌面端被动 SSH 检查同步修正。顺带 shallow 克隆的更新状态改为只报「有更新可用」而不是编造「1 个变更」。

内存/磁盘压力提示 + OOM 检测

  • e11d1ddc7|feat(status): surface memory pressure and suspected-OOM restarts to users (NS-656)
  • 6977d21fa|feat(gateway): disk-usage telemetry + dashboard disk-pressure banner (NS-656)

宿主 agent 可能每小时被 OOM 杀掉，而 dashboard 和 NAS 卡片看起来完全健康——所有内存信号（心跳采样、生命周期账本的非正常退出判定、缓存压力逐出）都死在服务端日志里。这个改动是读侧修复：新的 gateway/memory_status.py 把现有 30 秒心跳（进程 RSS + 系统 MemAvailable/MemTotal + swap）和生命周期哨兵蒸馏成紧凑的 memory 块：压力 ok/elevated/critical/unknown 分级、粗略 MB 数字、上次启动的非正常退出/suspected-OOM 标记。纯文件读取，不加新采样不加网关 IPC；心跳过期（>150s）或未来时间戳降级为 unknown，死网关的最后一口「critical」不会永远挂着。生命周期账本 record_startup 现在把 prior_unclean_exit / prior_suspected_oom 带到哨兵上（之前只存在于追加式诊断文本里）。/api/status 提供该块，故意不并入整体健康度——内存压力是提示性的，翻成 degraded 会把 NAS 可用性巡检也带崩。dashboard 新增 MemoryPressureBanner，按 critical > suspected-OOM > elevated 触发，按会话关闭、再次升级会重新弹出。磁盘侧同理：disk_status.py 采样 HERMES_HOME 的磁盘用量，critical 判定 <256MB 空闲或 ≥95% 占用，elevated <512MB；disk 块与 memory 并列，banner 优先级 disk critical > memory critical > OOM restart > disk elevated > memory elevated，关闭最上层会露出下一层而不是全部静音。针对的问题：agent 数据卷写满后 SQLite 写失败、会话停止持久化，而每个 dashboard 都看起来正常。

密码提供商原生登录（系统浏览器自动填充）

  • 56f1afc83|feat(dashboard-auth): extend RFC 8252 native sign-in to password providers (system-browser autofill) (#75808)

桌面端跑密码登录的 gated gateway 时用内嵌 Electron BrowserWindow，macOS 密码管理器/钥匙串自动填充够不到 Chromium-in-Electron 的表单——/login 表单明明带了对的 autocomplete 属性，用户还是得手打凭据。现有的 RFC 8252 原生流程（系统浏览器 + loopback + PKCE）对 OAuth 提供商正好解决这个问题，但之前以「密码提供商没有 IDP 往返可代理」为由禁用。这个改动把它打开：/auth/native/authorize 接受 supports_password 提供商，注册 pending 授权后 302 系统浏览器到交互式 /login 表单，凭据校验成功就按 /auth/callback 原生分支完成授权——铸造一次性 loopback 码、返回 loopback 重定向、清 PKCE cookie、不设会话 cookie。失败干净：代理过期返回 400 提示重新登录，凭据错误保留 pending 条目允许重试。纯网关改动，桌面端不用更新，旧桌面端构建等网关广告能力后自动生效。

  • e1caf88c6（高危）：Windows 上所有破坏性命令此前静默绕过审批。根因两个：DANGEROUS_PATTERNS 危险模式是 POSIX 形状的，Windows 的 Remove-Item/del/taskkill/Format-Volume/diskpart/reg delete 等一个都匹配不上；且路径归一化器把反斜杠当 shell 转义符剥掉，任何 Windows 路径都匹配不了路径规则。修复前实测 15/15 个破坏性命令（Remove-Item -Recurse -Force、del /s /q、iwr | iex、taskkill /F、Format-Volume、diskpart、icacls /grant Everyone、vssadmin delete shadows、bcdedit /set、reg delete、cipher /w…）全部逃过检测，修复后按规则拦截。

桌面端 HUD 模式（本期最大亮点）：

HUD 模式是桌面端新增的一种悬浮交互形态：一个无边框、透明、始终置顶的小窗口，复用应用自身的真实聊天界面，只改变窗口框架——没有标题栏、没有状态栏、没有窗格树。窗口底部是输入框，上方消息带以渐隐方式显示：回合进行中或输入框聚焦时保持可见，空闲后逐渐淡出，鼠标可以穿透到背后的应用。用户可以通过标题栏按钮或快捷键（macOS 为 ⌘⇧H）随时进入 HUD 模式（e8b83f37c、6a01b429d）。

HUD 里的会话交接做得比较完整：因为网关把一个会话的事件流绑定到唯一 socket，HUD 里开始的一轮对话只会在 HUD 里流动，关闭 HUD 时主窗口会自动恢复该会话、重建传输并接续进行中的回合，不会丢上下文（7b0dbd224）。

HUD 模式下 agent 能感知自己的悬浮状态：桌面端给 HUD 提交打上 surface: 'hud' 标记，网关把它转成每回合的提示，指向新加的 read_window_below 工具——agent 可以查询 Hermes 窗口底下是哪个应用窗口（应用名、标题、位置，仅元数据不读像素），回答"你下面是什么窗口""帮我查天气"这类问题时直接针对用户正在用的应用操作（e24bac49f、406501fd9、f22ae7292）。工具调用前会先检查 agent 自己的 schema，没有 computer_use 或 read_window_below 的会话不会被指向调不了的工具。

HUD 消息带改用 macOS 原生毛玻璃（vibrancy）渲染，三档渐隐：刚落地时半显示供扫一眼、聚焦时提升到可读、空闲后收起滑到输入框后面。只有空闲记录才会淡出，运行中的回合或等待用户回复时保持打开（4500b4391）。从其他标签页唤出 HUD 时会正确重定向到当前查看的会话（f444e0c5e），一批 HUD 细节修复同步合入（窗口尺寸、面板显隐、鼠标穿透边界、对话框下不穿透等：0e260b3c8、6ada733f9、c5332b2f8、843c3abcc、f9860b050、717b49c08、48d672e49、ba4456ab0、f03fc4684）。
